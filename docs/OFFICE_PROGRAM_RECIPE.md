# Office Program Recipe: One Program Manager over Several Area Coordinators

This recipe configures an office Orchestra installation (`https://<server>`) where each direct report (`<person>`) owns an area project (`<area>`) with their own coordinator agent (`<agent>`), and one program manager (`<pm>`) tracks all areas and messages each area's coordinator from the website. Every behaviour is cited against `main` (`file:line`).

## 1. Accounts, Projects, and Roles

Orchestra has four per-project roles — `viewer`, `contributor`, `coordinator`, `owner` (`http_authority.py:386-398`) — and no organisation or manager hierarchy:

1. **Create accounts and projects (`<area>` per direct report, plus `<program>`).**
   - A superuser creates each `<person>` and `<pm>` account on **People & access** (`#/admin/users`, `web/js/routes.js:45`, `web/js/views/admin.js:94-113`) and issues a reset code to set each password (People's **Add by username** requires an existing account, `web/js/views/project.js:1041,1051`).
   - On a fresh host-backed install, **Projects → Create a project** (`#/projects`, `POST /v1/projects` with `"create": true`, `web/js/views/work.js:163-191,350`, `http_service.py:8551-8555,8894-8898`) creates and registers a project directly; **Register a project** only registers one an operator already made with `admin.py add-project NAME` (`web/js/views/work.js:144,319`, `http_service.py:9095-9097`). Either the superuser creates (or registers) each `<area>` and `<program>` and adds `<person>` / `<pm>` as `owner` on **People** (and may step down), or grants them project creation under **People & access → Who may create projects** (choosing the **Account**, **Projects at one time**, and clicking **Allow creating projects**, `web/js/views/admin.js:40-84,114`, `PUT /v1/accounts/{uid}/project-grant`, `http_service.py:9073-9081`) so they use **Create a project** themselves.
   - `<pm>` must be a person `owner` of `<program>` (not only `coordinator`), because only a person `owner` accepts or retires `program.area.<area>` links (`http_service.py:13239-13245`).
2. **Add `<pm>` to each `<area>` as `contributor` (not `viewer`).**
   - On `#/p/<area>/people` (**People**, `PUT /v1/projects/{pid}/members/{uid}` or **Invite someone or add an agent**, `web/js/views/project.js:1130-1152`, `web/js/views/invites.js:32,52`, `http_service.py:10131-10144`), `<person>` adds `<pm>` as `contributor`.
   - Why `contributor`: `CAP_READ` lets `<pm>` see the area on the Program page (`http_service.py:13615-13621`), and `contributor` or above (`MEMBER_NOTE_ROLES`) is needed to message `<area>`'s coordinators (`http_auth.py:3981`, `http_service.py:10899-10937`). A `viewer` can read but not send member notes.
   - Add each `<person>` to `<program>` as `contributor` on `#/p/<program>/people` to read program requirements, file suggestions (`docs/design/PROGRAM_DESIGN.md:145-146`), or propose `program.area.<area>` when `approval_by_another_party` is on (Section 2).
3. **Grant each `<person>`'s coordinator agent the coordinator role in `<area>`.**
   - `<person>` creates a personal agent on **My agents** (`#/agents`, `POST /v1/agents`, `web/js/routes.js:14`, `http_service.py:11023`) and grants it `<area>` (only projects the owner belongs to, `http_auth.py:3315-3352`).
   - On `#/p/<area>/agents` (**Agents**), `<person>` clicks **Make coordinator** (`PUT /v1/projects/{pid}/agents/{aid}/coordinator`, `web/js/views/project.js:1111,1155-1166`, `http_service.py:11458-11469`). The grant applies only while the agent is enabled, holds `<area>`, its owner is `coordinator` or `owner`, and the issuer still holds project admin (`http_auth.py:4663-4716`, `http_authority.py:858-891`).

## 2. Link Each Area to the Program (Both Sides Owner-Accepted)

A program is an ordinary project linked to each `<area>` by two reference records, each backed by a native `decision` issue (`docs/design/PROGRAM_DESIGN.md:62-97`, `program_links.py:1-18`):

| Side | Project | Reference key | Exact two-line statement | Who proposes / who accepts |
| --- | --- | --- | --- | --- |
| Program | `<program>` | `program.area.<area>` | `Area: <area>`<br>`State: in` | Any `contributor` or above proposes (`approval_by_another_party` on: another party such as `<person>` as `contributor`); person `owner` `<pm>` (or host operator) accepts |
| Area | `<area>` | `program.member-of` | `Program: <program>`<br>`State: in` | Any `contributor` or above proposes (`approval_by_another_party` on: another party such as `<pm>` as `contributor`); person `owner` `<person>` (or host operator) accepts |

**When `approval_by_another_party` is enabled** (`--approval-by-another-party` or `"approval_by_another_party": true`, off by default; `docs/HTTP_DEPLOYMENT.md:2289-2292`, `http_service.py:12920-12950`, `record_acceptance.py:42-95`): a proposer cannot accept their own party's draft, and only a person `owner` can accept a `program.` key (`http_service.py:13239-13245`). The project `owner` creates the `decision` issue (step 1 — **Add a child task** requires `can_coordinate`, `web/js/views/children.js:13`, and **New task** has no type field, `web/js/views/task.js:34-38`; `docs/design/PROGRAM_DESIGN.md:91-94`), another party (`contributor` or above, `CAP_RECORDS`, `http_service.py:13236`; `viewer` lacks it, `http_authority.py:387`) proposes the reference record (step 2 — e.g. `<pm>` in `<area>`, `<person>` in `<program>`), and the person `owner` accepts it (step 3 — or a host operator accepts on the host, `program_links.py:11-12`). With it off, the `owner` may do all three steps.

Steps on each side (repeat for each `<area>`):

1. **Create a decision issue** in that project. A new project has no task yet, so first create one on `#/p/<pid>/new` (**New task**, `web/js/views/task.js:29-51`); then open `#/p/<pid>/t/<tid>` and use **Add a child task** with type `decision` and headings `## Decision`, `## Rationale`, `## Alternatives Considered` (`web/js/views/children.js:9-37`), noting `<decision-id>`.
2. **Propose the reference record** on **Records** (`#/p/<pid>/records`, **Propose a reference record**, `POST /v1/projects/{pid}/references`, `web/js/views/records.js:456-486`, `http_service.py:13467-13471`). Required fields (`web/js/views/records.js:458-482`): `Key` (`program.area.<area>` or `program.member-of`), `Title`, `Owner`, `Review by (YYYY-MM-DD)`, `Authority type` (`decision`), `Authority target` (`<decision-id>`), and `Statement` (the exact two-line statement above, `program_links.py:51-61`). To leave later, revise to `State: left`.
3. **Accept the draft as a person owner** on `#/p/<pid>/records/references/<key>` (`POST /v1/projects/{pid}/references/{key}/accept`, `web/js/views/records.js:866,879-884`, `http_service.py:13561-13565`), entering **Acceptance evidence**. Only a person `owner`'s web session (or host operator) can accept or retire a `program.` key; coordinators and agents are refused (`http_service.py:13239-13245`, `program_links.py:38-40,100-112`).
4. **Verify link state:** open `#/p/<program>/program` (Section 5) or `#/p/<pid>/records`, or query `GET /v1/projects/<program>/program-links` (`http_service.py:13726-13756`). A link is `linked` only when both live owner acceptances count (`program_view.py:87-95`); otherwise `one-sided`, `proposed`, or `left`.

## 3. What Each Person Sees and Cannot See

- **A program link grants nothing** (`docs/design/PROGRAM_DESIGN.md:139-165`, `program_links.py:16-18`). Every cross-project read re-checks live `CAP_READ` per project (`http_service.py:13611-13695`, `http_authority.py:1278-1287`).
- **`<pm>`** (`owner` of `<program>`, `contributor` in each `<area>`): sees each linked readable `<area>`'s open tasks, coordinators, lane counts, and all lane rows on `#/p/<program>/program` — the `<area>` owner's acceptance is the consent widening `<pm>`'s view from `own` to `all` when `<pm>` coordinates `<program>` (`http_service.py:13578-13609`, `program_view.py:150-161`). If `<pm>` is removed from an `<area>`, the next read shows it as `not visible to you` (no rows or counts); if `<pm>` stops coordinating `<program>`, the area lanes narrow to `own` (`http_service.py:13659-13672`, `web/js/views/program.js:23-27`); removed from `<program>`, the page is not found (`http_service.py:13623-13629`).
- **Each `<person>`** (`owner` of their `<area>`): sees all of their own `<area>` and **nothing** in another `<person>`'s `<area>` unless added there. On `#/p/<program>/program` (if a `<program>` member), an unshared `<area>` shows only its link state and `not visible to you`, with no counts or lanes (`http_service.py:13615-13621`, `web/js/views/program.js:23-27,36-37`).
- **Agents**: each personal agent reaches only projects in its live grant list, capped by its owner's live role; other projects return `404 Project not found` (`http_authority.py:831-855,1218-1233`).

## 4. Approvals by Coordinator Agents (`Settings`)

On `#/p/<area>/settings` (**Settings** → **Approvals by coordinator agents**, `PUT /v1/projects/{pid}/agent-approval`, `web/js/views/project.js:919-954,1244`, `http_service.py:9728-9748`, `http_auth.py:4729-4750`), only a project `owner` or superuser by web session may choose:

- **`by-agent` (default):** `<person>`'s coordinator agent may approve work delivered by another personal agent of `<person>` (or a sole-held worker credential name), never its own work or `<person>`'s bare account id (`http_authority.py:579-586,736-785`). This lets one `<person>` run a coordinator agent and separate worker agents in `<area>`.
- **`by-person` (strict):** all agents of `<person>` count as one party, so `<person>`'s coordinator agent never approves work by `<person>` or any other agent of `<person>` (`web/js/views/project.js:940-942`).

## 5. Watching Progress and Talking to Each Coordinator

- **Program page (`#/p/<program>/program`):** the left-rail **Program** entry reads a server-cached flag (`web/js/app.js:179-180`, `web/js/views/program.js:9-11`, `program_view.py:103-108`) refreshed on web accept/retire of `program.` keys (`http_service.py:13285-13299`). If the link was accepted on the host by an operator instead of through the web UI, the rail entry does not appear until `#/p/<program>/program` is opened once by URL (which refreshes the cached flag, `http_service.py:13717`). The page shows coverage, each area's open tasks, coordinators, `waiting_too_long`, `expect_by_passed`, `your_move_idle`, and a collapsed **Lanes (`<n>`)** drill-down (holder, task, state, waiting on, expect-by, flags; up to 50 lanes) linking straight to `#/p/<area>/lanes` (`http_service.py:13611-13716`, `web/js/views/program.js:35-65`).
- **Area Lanes page (`#/p/<area>/lanes`):** `GET /v1/projects/{pid}/lanes` (`http_service.py:15818-15874`, `web/js/views/project.js:521-546`). As a `contributor` (not `coordinator`) in `<area>`, `<pm>`'s direct Lanes view is scoped to `own` (`http_service.py:16154-16169`), whereas `#/p/<program>/program` shows all lanes of `<area>` over the live `linked` program link (`http_service.py:13578-13609`, `program_view.py:150-161`).
- **My work (`#/`, `GET /v1/me/work`):** `<pm>`'s assigned work across up to 50 memberships, plus review attention (`to_review`) only in projects where `<pm>` holds approval authority (`CAP_APPROVE`, i.e., `coordinator` or `owner`, `http_service.py:151,16172-16210,16241-16250`, `web/js/views/work.js:76-95`) — so as `contributor` in `<area>`, `<pm>` does not see `<area>`'s review queue there.
- **Messaging an area's coordinator (`#/p/<area>/notes`):** as a signed-in `contributor` (or above) in `<area>`, `<pm>` opens `#/p/<area>/notes` (from **Settings** → **Notes between coordinators**, `web/js/views/project.js:1243`, or by URL) and uses **Write to this project's coordinators** (`POST /v1/projects/<area>/notes` with `to: "coordinators"`, `web/js/views/notes.js:89-101,119-162`, `http_service.py:10864-10938`).
  - Only `<pm>` (`GET /v1/projects/<area>/notes?box=mine`) and `<area>`'s coordinators (`box=to` / `box=sent`) read the thread (`http_service.py:10939-10982`).
  - An unsettled member note wakes `<area>`'s coordinator agents with a pointer only; coordinators reply with `to: "member"` and `reply_to` (or mark noted via `POST .../noted`) (`docs/design/MEMBER_NOTES_DESIGN.md:22-55`, `http_service.py:10912-11003`). Unread replies appear on Notes via `GET /v1/me/notes` (`http_service.py:11005-11020`, `web/js/views/notes.js:148-158`). Limits: 4000-character plain text (`NOTE_TEXT_MAX`, `http_auth.py:3968-3981,4153`), 10 member notes/hour per person and project, 60 coordinator replies/hour.
  - A note is a request, not an instruction: the coordinator weighs it against its brief and `<person>`'s direction (`web/js/views/notes.js:94`, `web/js/agentSetup.js:602`).

## 6. What Does Not Exist Yet

- **No manager / direct-report concept:** searching the repository for `direct_report|direct-report|reports_to|line_manager|org_chart|subordinate|reporting_line` finds no matches; authority is strictly per-project membership plus explicit owner-accepted program links (`http_authority.py:386-398`, `program_links.py:1-18`).
- **No one-step program-linking UI:** linking an area still requires creating a `decision` issue and proposing/accepting the `program.area.<area>` and `program.member-of` reference records on `#/p/<pid>/records` (`web/js/views/records.js:456,866`).
- **No left-rail link to Notes:** `projectSections` omits `notes` (`web/js/app.js:169-196`); open `#/p/<area>/notes` from **Settings** (`web/js/views/project.js:1243`) or by direct URL.
- **No SSH enforcement of `by-person` approval:** over SSH the host route compares actor names, so an agent of the same person is never refused; setting `agent_approval` to `by-person` is enforced on the web route and web integration only (`docs/HTTP_DEPLOYMENT.md:2522-2523`).
